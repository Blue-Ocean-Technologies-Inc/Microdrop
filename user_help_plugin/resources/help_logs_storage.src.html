Help, Logs & Saved Files

Where to get help inside MicroDrop, how to read its log, and where MicroDrop keeps every file it writes: your experiments, devices and protocols, your settings, and the log file support will ask you for.

Start with the short walkthrough. The rest is a reference. Near the end are two lookups: Where is my …? and What to send support.

Overview

MicroDrop keeps what it writes in three places. Knowing which is which tells you what to back up, what is safe to reset, and what is gone when MicroDrop closes.

Your MicroDrop documents

Experiments (logs, run reports, data, pictures, videos), device files and protocols. Your data: back it up.

In your home folder: Documents\Sci-Bots\Microdrop (with / instead of \ on macOS, Linux and the Pi).

The settings folder

Preferences, window layout, layout presets, camera alignment. Safe to reset, with MicroDrop closed.

Windows: %APPDATA%\Sci-Bots\Microdrop. macOS, Linux and the Pi: in your home folder, .sci-bots/Microdrop (hidden: the name starts with a dot).

Memory only

Live values the parts of MicroDrop share while it runs, such as which experiment is open. Not saved: gone when MicroDrop closes.

<home> is your home folder: C:\Users\<your user name> on Windows, /Users/<your user name> on macOS, /home/<your user name> on Linux and on the Raspberry Pi instrument. On Windows, %APPDATA% is <home>\AppData\Roaming.

The program itself sits in the MicroDrop launcher folder, wherever MicroDrop was installed. Plugins you install go there too. Do not keep your own files in it.

Quick walkthrough

Five steps: find help, read the log, find the log file, report a problem, and open the folders.

  1. 1Tour the Help menu

    Click Help, the last menu in the menu bar. Open Changelog...: the window MicroDrop Changelog lists the changes in each release, newest first. The first heading is the newest release your copy contains; quote it when you ask for support. Close it and open About MicroDrop..., an illustrated overview of how MicroDrop is built.

    Tutorials ▸ lists these pages. Each entry is described in The Help menu.

  2. 2Open the console log and show only problems

    Click View ▸ Microdrop Console Logs. The pane is not part of the default layout; ticking it docks it in the window. The newest line is on top.

    Untick Debug and Info: only warnings and errors are left (critical lines always show). Set Buffer to 1000 so older lines stay in the pane; it starts at 10. Double-click a line to read it whole.

  3. 3Find the log file

    Click Open Log File at the bottom of the pane: the file MicroDrop is writing right now opens in the program your computer uses for .log files.

    To see it in its folder, use File ▸ Experiments ▸ Open Experiment Folder, or click the underlined experiment name after Experiment: above the protocol tree. The log is in logs.

  4. 4Report a problem

    Help ▸ Report an Issue... opens MicroDrop's GitHub Issues page in your web browser. Help ▸ Contact Support ▸ Technical Support opens a new email to support@sci-bots.com in your email program.

    Either way, attach the log file from step 3, the protocol, the run report if there was a run, and a screenshot. The checklist builds the list of files for you.

  5. 5Open the Experiments folder and the settings folder

    Open the experiment folder as in step 3, then go up one level: that is Experiments, one folder per experiment. One more level up are Devices and Protocols.

    No menu item opens the settings folder. On Windows, type %APPDATA%\Sci-Bots\Microdrop in the address bar of File Explorer. On Linux and the Pi, open your home folder, press Ctrl+H to show hidden folders, then open .sci-bots ▸ Microdrop. On macOS, in Finder choose Go ▸ Go to Folder… and type ~/.sci-bots/Microdrop.

Feedback, issue or support email

Three ways to reach the people who make MicroDrop. Pick by who should see it.

Send Feedback... is a form for ideas and opinions. Report an Issue... files a bug or a feature request on GitHub, where anyone can read and follow it; posting needs a free GitHub account. Technical Support is a private email to the support team; General Inquiries is for anything else.

A bug you can describe without private data: Report an Issue. A problem with your instrument, your results, or files you cannot share in public: Technical Support. A suggestion: Send Feedback.

Report an Issue and Contact Support do not attach anything for you. Add the files yourself: see What to send support.

Changelog and What's New

What changed in each release of MicroDrop.

Changelog... opens the whole list in the window MicroDrop Changelog. At start, when MicroDrop has been updated since you last ran it, a What's New? window shows only the sections added since then.

After an update, to see what is different. Before asking for support, to read which release you have.

Newest release first. The first heading is the newest release your copy contains.

The very first start shows no What's New?: MicroDrop only notes the list then. It keeps that copy as .previous_changelog in the settings folder.

Tutorials

Plain-language pages like this one, one per part of MicroDrop.

Each loaded plugin can add its pages; the submenu lists them in a suggested reading order, starting with Getting Started with MicroDrop, and follows plugins switched on or off while MicroDrop runs. The pages work offline. A tutorial opens in its own window, or in your web browser on computers where MicroDrop cannot show web pages itself.

The image-analysis terms (ROI, trend fits and so on) are in Image Analysis Tutorial.

Beta notice

A one-time notice at first start: MicroDrop is open-source beta software, provided without warranty.

It asks you to check results in your own workflows and to back up your data. Once you have seen it, MicroDrop writes the marker file .beta_disclaimer_accepted in the settings folder and does not show it again.

Delete the marker file to see the notice again.

The console log

MicroDrop keeps a running diary of what it does: the log. You read it live in the Microdrop Console Logs pane, and every line also goes into a log file inside the current experiment folder.

Microdrop Console Logs pane

The log, live, newest line first.

A table with Time, Level, Source and Message. Above it are the level tick boxes and a search box; below it Reset Logs, Buffer, Open Log File and Copy Log to Clipboard. The table is dark in both light and dark themes.

When something looks wrong, when a message flashes by, or when support asks what happened.

Level is coloured: Debug purple, Info green, Warning orange, Error red, Critical bright red. Source names the part of MicroDrop that wrote the line, such as device_viewer… or pluggable_protocol_tree…. Hover over a message to see all of it. Double-click a line to open Log Details, where web links and the paths of files that exist become clickable.

Closed. Tick it in the View menu; the window remembers it next time.

Level filters

Which kinds of line the pane keeps.

One tick box per level. Critical lines always show; there is no box for them.

Untick Debug and Info to see only problems. Tick Debug only when support asks for detail.

Unticking a level removes its lines from the pane, and ticking it again shows only new ones. The log file is not affected: it keeps every line at the Level set in Preferences.

Debug off; Info, Warning and Error on. Your choice is remembered.

Search

Shows only the lines that contain some text.

Type in Search logs...; capitals do not matter. The list beside it picks where to look: All (source, message and level), Source or Message.

To follow one part of MicroDrop (search a source), or one word such as error or a file name.

Searching only hides lines. Clear the box and they are all back.

Empty, All.

Buffer

How many lines the pane keeps. When a new line arrives and the pane is full, the oldest is dropped.

Raise it before you watch a problem happen, so the lines that lead up to it are still there.

Only the pane is trimmed; the log file keeps every line.

10, the smallest allowed, so out of the box the pane shows only the last ten lines. Anything from 10 to 100,000; 1000 is a comfortable working value. Remembered.

Reset Logs, Open Log File, Copy Log to Clipboard

The three buttons under the table.

Reset LogsEmpties the pane. The log file is not touched.
Open Log FileOpens the file MicroDrop is writing now, in the program your computer uses for .log files.
Copy Log to ClipboardCopies the one line you last clicked, with its time, level and source, ready to paste into an email. Click a line first.

To send the whole log, attach the file (Open Log File shows you which one) rather than copying lines.

Log level

How much MicroDrop writes, to the pane and to the file.

Debug, Info, Warning, Error or Critical. Each level also writes the ones after it: Info writes info, warnings, errors and critical lines; Debug writes everything.

Set Debug when support asks for more detail, reproduce the problem, then set it back: Debug lines are many and the file grows fast. To see them in the pane, tick Debug there too.

It takes effect when you click Apply or OK.

Info.

The log file

A plain-text copy of the log, kept with the experiment it belongs to.

Its name is microdrop.frontend.<computer number>-<process number>.log. The computer number identifies the machine; the process number changes every time MicroDrop starts. A backend started on its own (a remote set-up) writes its own microdrop.backend.… file the same way.

Attach it to every bug report and support email.

One line per entry: date and time, [LEVEL:source], the message, then the program file and line that wrote it. Search the file for ERROR and WARNING.

A new file each time MicroDrop starts (it starts a new experiment folder), and each time you start a new experiment: the log moves on to the new folder's logs. MicroDrop never splits or trims a log file.

Where things are saved

The folders in detail. Open a folder in the map to see what is inside and what writes it; the cards below say when each matters and whether it is safe to delete.

Your MicroDrop documents folder

The folder for everything you make: experiments, device files and protocols.

MicroDrop creates it, with Experiments, Devices and Protocols inside, the first time it starts. Remote-Experiments appears if you sync experiments from an instrument over the network.

Back this folder up. Copy it when you move to a new computer.

MicroDrop builds the path from your home folder, so it is always <home>\Documents, even if your Documents library has been moved elsewhere, for example into OneDrive. No menu item opens it; open the experiment folder (File ▸ Experiments ▸ Open Experiment Folder) and go up two levels.

C:\Users\<you>\Documents\Sci-Bots\Microdrop, /home/<you>/Documents/Sci-Bots/Microdrop on Linux and the Pi.

Experiment folders

One folder per experiment, holding everything that experiment wrote.

The name is the date and time it began in UTC, as YYYY_MM_DD-HH_MM_SS. MicroDrop starts a new one each time it starts, and when you click New Experiment above the protocol tree or choose File ▸ Experiments ▸ New Experiment. The current one is named after Experiment: above the protocol tree; click the name to open the folder.

To find a run's report, data, pictures or log. To send support the files of one experiment.

InsideWhatWritten

Many folders hold only logs: MicroDrop was started and nothing was run. File ▸ Experiments ▸ Prune Experiments… moves every such folder, never the current one, to the Recycle Bin (Trash on macOS and Linux), after asking.

Device files and the default device

The device (chip) drawings MicroDrop can load, as .svg files.

At first start MicroDrop copies its two bundled files here, 90_pin_array.svg and pin_map.svg, if they are missing. Loading a device file from somewhere else copies it here; if a file of that name exists, MicroDrop asks whether to Overwrite it or Save As... a new name. Saving a device starts here too.

Copy a device file from here to share it, or to send it to support with a problem that involves the chip drawing.

The last device you load becomes the default for the next start, shown as Default Device Layout in Edit ▸ Preferences... ▸ Device Viewer ▸ Main View.

Devices\90_pin_array.svg. When the default is empty or its file is missing, MicroDrop goes back to this file and, if it differs from the bundled one, overwrites it with the bundled copy. Do not edit 90_pin_array.svg in place: save your changes under a new name.

Protocol files

Where the protocol Save, Load and import dialogs start.

A folder per device: the name of the loaded device file without .svg, or Null when no device is loaded. MicroDrop creates it when a dialog opens. You can save a protocol anywhere; this is only the starting point.

A protocol is a .json file. Each experiment also keeps the copy made at the end of each run, in its own protocols folder.

Protocols\90_pin_array.

AutoSave

Writes the open protocol back to its own file shortly after you stop editing.

About 1.5 seconds after your last change, AutoSave saves the protocol to the file it was last saved to or loaded from. It never picks a file for you: a protocol that has never been saved is not written. It waits while a protocol runs and saves held-back changes when the run ends, and it saves pending changes before the window closes.

Leave it on. Turn it off to try edits you might not keep, then use Save As if you want them.

The glyph in the status bar is green when AutoSave is on and grey when it is off; it and the AutoSave tick box above the protocol tree switch the same setting. Hover for its state: save the protocol once to start, changes are saved to <file> automatically, paused while the protocol runs, or the last save failed. If a save fails, an AutoSave Failed warning appears once; your changes stay in MicroDrop, the next change tries again, and Save As lets you pick another place.

On (remembered).

To reset MicroDrop's memory without touching your data, or to send support your settings.

On macOS, Linux and the Pi the folder name starts with a dot, so file browsers hide it until you show hidden files. The walkthrough's step 5 shows how to get there.

Windows: %APPDATA%\Sci-Bots\Microdrop. Elsewhere: <home>/.sci-bots/Microdrop.

preferences.ini

Your settings, in one text file.

Everything in Edit ▸ Preferences..., plus choices MicroDrop remembers for you: the console log filters and buffer, the protocol tree's columns, AutoSave on or off, the default device, camera settings, the capacitance calibration, zone types, and which plugin groups are switched on.

Send it to support when a problem might come from a setting. Delete or rename it to start again from the defaults.

Plain text, [section] headings with name = value lines. You do not need to edit it by hand.

MicroDrop writes most settings into it when it closes normally, so change it only while MicroDrop is closed: otherwise your edit is overwritten.

Bundled defaults

The starting values that ship with MicroDrop.

A second, small preferences.ini inside the program. It sets which screen MicroDrop opens on and that the last window layout is restored at start. Your own preferences.ini in the settings folder overrides it.

Part of the program: an update replaces it. Do not edit it.

Window layout and layout presets

Where each pane sits, and the arrangements you saved.

application_memento holds the layout as it was when you last closed MicroDrop; it is restored at start unless Always Use Default Layout is ticked (Edit ▸ Preferences... ▸ Microdrop General ▸ Application Startup). Presets made with View ▸ Layout Presets ▸ Save Current Layout... are files in layout_presets, one per preset, with shortcuts.json for their keys and default_preset.txt naming the one Reset Layout uses.

A pane you cannot find: View ▸ Reset Layout, or tick it in the View menu. A window that opens broken: close MicroDrop and delete application_memento.

If MicroDrop cannot restore the saved layout at start, it opens with the default one and ticks Always Use Default Layout for you; untick it to have your layout restored again.

Camera alignment cache

The saved camera alignment endpoints, kept per device file name.

Each endpoint is the four corners where the device drawing should land on the camera picture. They survive restarts and device switches. The Camera & Alignment Tutorial covers how to make them.

Deleting the folder or the file drops every saved endpoint; you place them again.

Installed plugins

Plugins you add with Tools ▸ Manage Plugins….

MicroDrop installs them with pixi into its own environment: the plugin is added to pyproject.toml and pixi.lock in the launcher's microdrop-py folder, and its files go into microdrop-py\.pixi. Which plugin groups are switched on is kept in preferences.ini.

Add, update and remove plugins only through Manage Plugins; never delete their files.

What is not saved

A shared notice board the parts of MicroDrop use while it runs.

The message server keeps live values such as the current experiment folder, the loaded device file, the electrode areas and the camera captures of the current run. The server MicroDrop starts keeps nothing on disk and stops when MicroDrop closes.

MicroDrop fills it again from your files and settings at the next start. What you notice: a new experiment folder at each start rather than the last one. In the same way, Browse session reports lists only the reports made since MicroDrop started.

Caveats

  • Logs live inside the experiment folder. Each start and each New Experiment begins a new log file in a new folder. Send the log of the experiment in which the problem happened.
  • Experiment folder names are in UTC, not your local time; run reports and data files use local time.
  • The Console Logs pane keeps only 10 lines until you raise Buffer.
  • Unticking a level in the pane throws its lines away; the log file still has them.
  • Copy Log to Clipboard copies one line, the last one you clicked. Attach the file instead.
  • Log files are never trimmed. A long session at the Debug level makes a large file.
  • Check before you post in public. Log lines, reports and file names carry folder paths, which can include your user name, and the log file's name carries a number that identifies the computer. Use Technical Support for anything private.
  • Deleting preferences.ini resets every preference, along with the remembered choices (default device, column layout, calibration, plugin groups). Do it with MicroDrop closed: it rewrites the file as it closes.
  • Deleting .device_viewer_cache drops all camera endpoints.
  • Settings are written when MicroDrop closes normally. If it crashes, settings changed in that session can be lost.
  • Do not edit Devices\90_pin_array.svg in place: MicroDrop may replace it with the bundled copy. Save changes under a new name.
  • No menu item opens the settings folder, Devices or Protocols. Use the paths on this page; the device and protocol file dialogs start in their folders.
  • Paths differ by computer. On macOS, Linux and the Pi the settings folder is the hidden <home>/.sci-bots/Microdrop; folder separators are / instead of \.

Glossary

Log
MicroDrop's running diary of what it does, one line per event.
Log level
How serious a line is: Debug, Info, Warning, Error, Critical.
Buffer
How many log lines the Console Logs pane keeps.
Experiment
A folder that collects one session's logs, run reports, data, pictures and videos.
UTC
Coordinated Universal Time: the world reference clock, without your time zone.
Documents folder
<home>/Documents/Sci-Bots/Microdrop: your experiments, devices and protocols.
Settings folder
Where MicroDrop keeps its own files: %APPDATA%\Sci-Bots\Microdrop on Windows, <home>/.sci-bots/Microdrop elsewhere.
Preferences
Your settings, edited in Edit ▸ Preferences... and kept in preferences.ini.
Device file
An .svg drawing of a chip's electrodes.
Endpoint
A saved camera alignment: where the device drawing lands on the camera picture.
Layout preset
A saved arrangement of the panes, applied from View ▸ Layout Presets.
AutoSave
Saving the open protocol to its file automatically, shortly after each change.
Message server
The part of MicroDrop (Redis) that passes messages and live values between its parts; it keeps nothing after MicroDrop closes.
Plugin
An add-on part of MicroDrop, such as support for a heater or a camera.
