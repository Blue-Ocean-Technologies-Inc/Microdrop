SSH & Remote Backend

Some instruments are driven by a second computer, for example a small computer inside the instrument, while you work in MicroDrop on your own PC. Tools ▸ Remote Controls helps with two jobs in that setup: putting an SSH key on the instrument computer once, and then copying its experiment folders back to your PC with one button.

This page also explains, in plain words, how the parts of MicroDrop talk to each other when they run on two computers, so you can tell what is wrong when something does not connect.

Overview

Remote Controls is a small menu with two windows. Both use the same saved settings.

  • SSH Key Portal… makes (or finds) a key on this computer and copies its public half to the instrument computer. You type the instrument computer's password once, for this upload. After that, the key is used instead of the password.
  • Sync Remote Experiments… (Ctrl+Shift+S) copies the instrument computer's Experiments folder into a folder on this computer named after the instrument. It copies one way only: from the instrument to you.
  • Edit ▸ Preferences… ▸ SSH / Remote Backend holds the same settings: host, port, user name, key name, the folder to copy from, and the folder name used on this computer.

The Remote Controls menu, its preferences tab and this tutorial come from one part of MicroDrop that is loaded with the MicroDrop window. Whether you see them depends on how MicroDrop was started:

Not the same as the portable instrument. The portable DropBot has its own small computer (a Raspberry Pi) that runs all of MicroDrop, window included, on its own screen. Nothing is split, so you do not need this page to use it. You can still use Sync Remote Experiments from your PC to copy the portable's experiments off it, if it is on your network and accepts SSH.

What Remote Controls does not do

  • It does not start, stop or connect to the remote backend. That is done when MicroDrop is started on each computer (see Setting up two computers).
  • It does not set where the message server is; that is a separate settings file (see Message server).
  • It never sends files to the instrument computer and never deletes files on either side.
  • It does not sync by itself on a schedule; it copies only when you press the button.
  • It shows no percentage and has no Cancel button. Closing the window does not stop a copy.
  • It cannot remove a key from the instrument computer again.

Who talks to whom

MicroDrop is built from three parts that pass messages to each other. On one computer you never notice. Split over two computers, each connection has to work.

  • Frontend: the MicroDrop window you click in.
  • Message server (a program called Redis): the post office. Every click becomes a message that goes to the server, and the server hands it to whoever needs it. Both other parts must reach it, at the address and port in the settings file redis_settings.json (normally 127.0.0.1, this computer, port 6379).
  • Backend: the part plugged into the DropBot by USB. It turns messages into hardware commands and sends readings back.

Remote Controls is a fourth, separate path: SSH, straight from this computer to the instrument computer. Key upload and Sync use only that path (plus the message server, to pass your button press to MicroDrop's SSH service on this computer). They do not need the backend or the DropBot.

Quick walkthrough

Four steps, from nothing to experiment folders on your PC. You need the instrument computer's address, a user name on it and that user's password. Steps 1 and 2 are needed only once.

The pictures below are drawings of the windows, not screenshots.

  1. 1Enter the instrument computer's address

    Open Edit ▸ Preferences… and pick the SSH / Remote Backend tab. Type the Host (for example dropbot.local or 192.0.2.10) and the Username (for example pi). Leave SSH Port at 22 unless you were told otherwise. The Device ID fills itself in from the host. The other values can stay as they are.

  2. 2Make a key and upload it

    Choose Tools ▸ Remote Controls ▸ SSH Key Portal…. Host, port and user name are already filled in. Type the Password of that user. Click Generate / Read Key: the status under it shows Success! Using key from: …. Then click Upload Generated / Read Public Key. A message Public key authorized on dropbot.local means it worked. See SSH Key Portal for everything that can happen here.

  3. 3Copy the experiments

    Choose Tools ▸ Remote Controls ▸ Sync Remote Experiments… (or press Ctrl+Shift+S in the main window). Check the Local destination line, then click Sync Remote Experiments. A moving bar appears and the status changes to Request sent, waiting for backend..., then Backend acknowledged, syncing.... When it is done, a Sync complete message appears and the window closes.

  4. 4Find the copies

    The folders are in Documents\Sci-Bots\Microdrop\Remote-Experiments\ followed by the Device ID, for example …\Remote-Experiments\dropbot_local. They sit next to your own Experiments folder, never inside it. Run Sync again any time: only new and changed files are copied.

SSH Key Portal

Tools ▸ Remote Controls ▸ SSH Key Portal… opens a separate window with three numbered boxes. Choosing the menu item again closes the open window and opens a fresh one.

  1. 1. Connection Details (for key upload): Host, Port, Username, Password. The first three come from your preferences, and what you type here is saved back to them straight away. The password is shown as dots and is not saved (see Password).
  2. 2. Generate or Read Key Pair: Local Key Name and the Generate / Read Key button. If a key with that name already exists on this computer, it is read and reused; otherwise a new one is made. The status line under the button shows where the two files are.
  3. 3. Upload Public Key to Server: the Upload Generated / Read Public Key button logs in to the instrument computer with the password and adds the public key to that user's list of trusted keys. If the key is already on the list, it is not added twice.

The order matters: Upload works only after Generate / Read Key has succeeded in the same session. Each button is greyed out while its job runs.

From key to password-free sync

Sync Remote Experiments

Tools ▸ Remote Controls ▸ Sync Remote Experiments… (Ctrl+Shift+S) opens a separate window. Its tooltip sums it up: Pull the remote backend's Experiments/ folder locally via rsync over SSH.

  1. 1. Remote Host: Host, Port, Username, Key Name. Same values as the Key Portal and the preferences; edits are saved straight away.
  2. 2. Paths: Device ID (editable), Remote source (the folder on the instrument computer, editable) and Local destination (where the copies go, worked out from the Device ID; you cannot type in it).
  3. 3. Sync: the Sync Remote Experiments button, a moving bar while it works, and Status.

What happens when you press Sync

  1. MicroDrop checks that Host, Username and Port are filled in, and that the private key file (.ssh\id_rsa_microdrop in your user folder) exists. If the Device ID is empty, it is set from the host.
  2. It creates the local destination folder if needed and sends the request. Status: Request sent, waiting for backend.... Here, and in Backend acknowledged, "backend" means MicroDrop's SSH service on this computer, not the DropBot backend.
  3. The service first checks, for up to 3 seconds, that the instrument computer answers on the SSH port. If it does, the status becomes Backend acknowledged, syncing... and the copy starts.
  4. The copy is made by rsync over SSH, logging in with your key. It never asks for a password.
  5. When it ends: Sync complete and the window closes, or an error message (see Messages) and the status goes back to Idle so you can try again.

Slow syncs and time limits

  • After 60 seconds without an answer, MicroDrop asks Still syncing: The remote sync is taking longer than expected. Keep waiting? (if no process will quit and finish in background). Yes waits another 60 seconds (status Still syncing...) and asks again if needed. No closes the window; the copy carries on in the background, but you will not see its result.
  • After 120 seconds of copying, MicroDrop stops the copy, whatever the reason, and shows Connection timed out. A big first sync can hit this limit even on a good network. The files already copied stay; press Sync again and rsync carries on with the rest.
  • Closing the window with its close button does not stop the copy either.

Device ID and destination

The Device ID follows the host as you type it, as long as you have not changed it yourself. Once you type your own name, changing the host leaves it alone.

What gets copied

Everything inside the remote source folder, sub-folders included, goes into the local destination. The slash at the end of the remote source matters: with it, the contents of Experiments are copied; without it, you get an extra Experiments folder inside the destination.

Toolbar icons

None. Remote Controls adds no toolbar buttons or icons. Both windows use text buttons: Generate / Read Key, Upload Generated / Read Public Key and Sync Remote Experiments.

Terms

Every setting in the two windows and the preferences tab, plus the words around them.

Host

The name or network address of the instrument computer.

Where SSH connects to. A name such as dropbot.local or a number such as 192.0.2.10. On first start it comes from REMOTE_HOST_IP_ADDRESS if that is set (see Where the values come from); otherwise it is empty.

Set it once per instrument. Change it to sync from a different computer.

A wrong or unreachable host gives Could not reach remote host within a few seconds of pressing Sync.

dropbot.local (a placeholder: ask whoever set up the instrument)

Port

The SSH "door number" on the instrument computer.

A whole number. On first start it is REMOTE_SSH_PORT if that is set, otherwise 22, the standard SSH port.

Change it only if the instrument computer's SSH listens somewhere else.

In the Key Portal, any text that is not a whole number pops up Port must be an integer., even for a moment while you retype it. Select the number and type over it instead of deleting it first.

22

Username

The account you log in as on the instrument computer.

The key is added to this user's trusted keys, and Sync copies from this user's home folder. On first start it comes from REMOTE_HOST_USERNAME, otherwise empty.

Use the account that runs MicroDrop on the instrument computer, so the experiments are in its home folder.

Shown as user@host in the remote source, for example pi@dropbot.local:~/….

pi (a placeholder)

Password

The instrument computer user's password, needed once for the key upload.

Used only by Upload Generated / Read Public Key. It is kept in memory until MicroDrop closes (reopening the Key Portal fills it in again) and never written to disk. Sync never uses it.

Type it right before uploading. After a successful upload you do not need it again.

Upload refuses to start with an empty password: All connection fields are required. A wrong one gives Authentication Failed. Please check your username and password.

Empty when MicroDrop starts.

Key name, public and private key

The name of the key file pair in the .ssh folder of your user folder on this computer.

An SSH key is a pair of files. The private key (id_rsa_microdrop) stays on this computer and proves who you are. The public key (id_rsa_microdrop.pub) is the half you hand out: a computer that has it on its trusted list lets the private key in. MicroDrop makes a 4096-bit RSA pair with no passphrase.

Keep the default unless you want a separate key per instrument. All three places share one value.

Spaces at the start and end are dropped. If the name is empty, Generate shows Key Name cannot be empty.

id_rsa_microdrop

Key upload

Copying the public key to the instrument computer's list of trusted keys.

MicroDrop logs in once with the password (10-second limit to connect), creates the user's ~/.ssh folder and its authorized_keys file if they are missing, and adds the public key as one line unless it is already there.

Once per instrument computer and key. Again if you make a new key or the instrument computer is reinstalled.

Success: Public key authorized on dropbot.local. You can now try connecting with your private key.

Done once.

Remote experiments path

The folder on the instrument computer that Sync copies from.

A path on the instrument computer; ~ means the user's home folder there. The default is where MicroDrop keeps experiments with standard settings.

Change it only if MicroDrop on the instrument computer saves experiments elsewhere.

Keep the slash at the end (see What gets copied).

~/Documents/Sci-Bots/Microdrop/Experiments/

Device ID

The name of the folder on this computer that holds one instrument's copies.

Made from the host by turning every character other than letters, digits, _ and - into _: 192.0.2.10 becomes 192_0_2_10, dropbot.local becomes dropbot_local. You can type your own nickname instead.

Give it a nickname when the instrument's address may change, so its copies stay in one folder.

The Local destination line shows the full folder it leads to.

The host, made folder-safe.

Local destination

Where the copied experiments land on this computer.

Documents\Sci-Bots\Microdrop\Remote-Experiments\ in your user folder, plus the Device ID. It is not a setting of its own: change the Device ID to change it.

Check it before the first sync of a new instrument.

Created on the first sync. Kept apart from your own Experiments folder.

C:\Users\you\Documents\Sci-Bots\Microdrop\Remote-Experiments\dropbot_local

rsync over SSH

The copying tool Sync uses, running through an SSH connection.

rsync compares both sides and copies only files that are new or differ in size or modified time. It keeps folder structure and file times. It runs on this computer and, through SSH, on the instrument computer. On Windows MicroDrop brings its own copy (rsync-win). On Linux and macOS this computer needs rsync installed. The instrument computer always needs rsync.

Every time you press Sync.

Errors from rsync itself appear as rsync exit plus a number, with rsync's own message.

A repeat sync with nothing new finishes quickly.

Remote backend

MicroDrop's hardware part running on another computer than the window.

The backend is started on the computer the DropBot is plugged into, without a window; your PC runs only the window. Both connect to one message server. Remote Controls does not start or watch it.

When the DropBot is attached to a different computer than the one you sit at.

If the window works but the DropBot does not react, check that the backend is running and reaches the message server (try the diagram).

Not used: most setups run everything on one computer.

Message server (Redis host and port)

Where the message server runs, which every MicroDrop part must reach.

Read from redis_settings.json in the MicroDrop program folder, next to redis_settings.example.json. Without that file MicroDrop uses host 127.0.0.1 (this computer only) and port 6379. Whenever MicroDrop opens a window through the normal start, it starts a server itself if none is running at that address; the window-only and backend-only start scripts do not. Remote Controls never changes this.

For a split setup, both computers' files must name the same host and port.

If it cannot be reached, MicroDrop logs Cannot reach the Redis server at <host>:<port> — is it running? and cannot start.

127.0.0.1, port 6379

Where the values come from

Host, port, user name, key name, remote path and Device ID are one set of saved values, shared by the preferences tab and both windows. Typing in either window changes the saved value at once.

  • Saved in MicroDrop's preferences.ini, in the section [microdrop.ssh_controls] (see the Help, Logs & Saved Files tutorial for where that file is).
  • First start only: host, port and user name are taken from the environment variables REMOTE_HOST_IP_ADDRESS, REMOTE_SSH_PORT and REMOTE_HOST_USERNAME. MicroDrop also reads them from a file named .env if there is one in the MicroDrop program folder or a folder above it. Once a value has been saved, these are no longer looked at.
  • No reset button. To go back to the first-start values, close MicroDrop and remove the [microdrop.ssh_controls] section from preferences.ini.
  • Not saved: the password.

Security notes

What the code does, so you can judge whether it fits your lab's rules.

  • The instrument computer's identity is not checked at upload. The Key Portal accepts whichever computer answers at the host address, without comparing its host key to a known one, and sends the password to it. Use it only on a network you trust, and double-check the host.
  • The upload request passes through the message server, password included. When the server runs on another computer, that request crosses the network unencrypted.
  • The message server has no password. Whoever can reach its address and port can send MicroDrop messages. Keep it on the lab network; with the default 127.0.0.1 only this computer can reach it.
  • The private key has no passphrase. Protect your user account on this computer. To withdraw access, remove the key's line from authorized_keys on the instrument computer.
  • Sync uses only the key, never the password. On Linux and macOS it uses the system's ssh without letting it ask questions, so, unless your SSH is set up otherwise, it refuses an instrument computer it does not already know (Host key verification failed.). Connecting once with ssh pi@dropbot.local in a terminal and checking the fingerprint records it.

Setting up two computers

For whoever installs the instrument. Remote Controls does none of this; it is how MicroDrop is started.

  1. Choose which computer runs the message server. In its redis_settings.json, set "host" to that computer's network address (with 127.0.0.1 no other computer can connect) and keep "port" at 6379. Start the server there: redis-server, or pixi run python examples/start_redis_server.py. Run this and the commands below from the MicroDrop source folder, microdrop-py/src.
  2. Give the other computer a redis_settings.json with the same host and port.
  3. On the computer with the DropBot, start the backend only: pixi run python -m examples.run_device_viewer_pluggable_backend (add --device opendrop or --device portable for those instruments).
  4. On your PC, start the window only: pixi run python -m examples.run_device_viewer_pluggable_frontend. It includes Remote Controls and its SSH service.
  5. For Sync, the instrument computer also needs an SSH server, rsync and a user account; then follow the walkthrough.

Caveats

  • One way only. Sync copies from the instrument computer to this one. Nothing goes back, and nothing is deleted on either side.
  • Local edits can be overwritten. If you change a copied file here and the instrument's version differs, the next sync replaces yours. Work on a copy outside Remote-Experiments.
  • Password once. The password is needed only for the first upload; after that the key is used. The instrument computer must allow password logins for that upload.
  • rsync on both ends. The instrument computer needs rsync; on Linux and macOS so does this one. Windows uses MicroDrop's own copy.
  • Closing the window does not stop a sync. Neither does answering No to Still syncing. There is no Cancel.
  • Two-minute limit. A sync that runs longer than 120 seconds is stopped with Connection timed out. Press Sync again to continue.
  • A lone private key gets replaced. If .ssh\id_rsa_microdrop exists without its .pub file, Generate / Read Key makes a new pair over it. Upload the new key afterwards.
  • Port box in the Key Portal. Deleting the number pops up Port must be an integer.; type over it instead.

Glossary

SSH
Secure Shell: the standard, encrypted way to log in to another computer over a network and copy files.
Key (key pair)
Two matching files that replace a password: a private key you keep, a public key you give to computers that should let you in.
Host
A computer on the network, named by its address.
Port
A numbered door on a computer; SSH normally uses 22, the message server 6379.
Redis
The program MicroDrop uses as its message server.
Frontend
The MicroDrop window.
Backend
The part of MicroDrop that drives the DropBot; it has no window.
rsync
A copying tool that copies only what is new or changed.
Device ID
The folder name MicroDrop uses on this computer for one instrument's copies.
Instrument computer
On this page: the remote computer you sync from, usually the one next to the DropBot.
